ChaosFilter

A Rust workspace that combines a CLI controller with an eBPF program (via Aya) to inject controlled chaos into Linux systems—such as network impairment (delay/loss) and resource stress controls.

Project overview

What it does

ChaosFilter is built to inject failure conditions in a controlled, repeatable way. It helps you exercise resilience—timeouts, retries, backpressure, and fallbacks—against realistic Linux behavior.

  • Network impairment: delay and packet loss on an interface
  • Config-driven: one TOML file describes a run (“plan”)
  • eBPF under the hood: integrates with the kernel via Aya
How it’s used

The CLI reads a config, validates it, then applies injectors for a scheduled duration. You need a capable Linux host: eBPF, bpftool, traffic control (tc), and enough memlock for maps—see Environment setup below.

Quick help
cargo build
cargo run -- --help

Environment setup (Linux)

What follows is the essential baseline for ChaosFilter on Linux: installs and checks the CLI and eBPF injectors actually need—not every possible kernel or distro requirement, just what this page walks through.

System packages

Why: ChaosFilter is a Rust binary that loads eBPF programs into the kernel and uses tc (iproute2) for impairment. On the host where you run it, those code paths expect bpftool, tc, and the other networking utilities in this list—that is run time. The same line also installs a compiler, LLVM, and kernel headers if you build the workspace on this machine; omit or trim those if you only deploy a prebuilt binary elsewhere.

Run this on Debian/Ubuntu to install that baseline (adjust for your package manager): 

sudo apt update
sudo apt upgrade -y

sudo apt install -y \
  build-essential \
  clang \
  llvm \
  libelf-dev \
  zlib1g-dev \
  libclang-dev \
  linux-headers-$(uname -r) \
  pkg-config \
  bpftool \
  iproute2 \
  iptables \
  net-tools \
  curl
Rust + BPF target

Why: The CLI and orchestration are Rust; the chaosfilter-ebpf crate compiles to eBPF bytecode, which requires Rust plus the bpfel-unknown-none rustup target.

Run this to install Rust (via rustup) and add that target:

curl https://sh.rustup.rs -sSf | sh
source $HOME/.cargo/env

rustup target add bpfel-unknown-none
Kernel eBPF features

Why: Before you chase load errors, it helps to see which BPF-related features your kernel advertises. ChaosFilter loads eBPF programs; this command summarizes what the kernel claims to support.

Run this to print that summary:

bpftool feature
cgroup v2

Why: CPU/memory and block injectors use cgroup v2 controllers; they assume a unified hierarchy—not legacy cgroup v1.

If you want to see whether your system is using cgroup v2, run this (it prints the filesystem type of the cgroup mount): 

stat -fc %T /sys/fs/cgroup/

You should see cgroup2fs.

memlock

Why: Loading maps and programs can exceed the default locked-memory cap for your shell session; the loader may fail until the limit is raised. For a permanent limit, use systemd or /etc/security/limits.conf per your distro.

Run this in the shell you use to build or run ChaosFilter (session only):

ulimit -l unlimited
File descriptor limits (inspect)

Why: The filesystem injector raises or lowers RLIMIT_NOFILE (max open files) for one process ID—the target_pid you set in config. That is a per-PID rlimit (process resource limit), not a cgroup controller limit; cgroup v2 doesn’t own this path. When debugging, read soft/hard NOFILE for that same PID.

Run one of these with the real PID in place of <pid>:

cat /proc/<pid>/limits
# or
prlimit --pid <pid>

Usage

Commands you can run: the blocks below are example invocations of the chaosfilter CLI (through cargo run after cargo build)—validate, run chaos from a TOML, and (in the second card) scaffold a file with init.

Validate a config
cargo build
cargo run -- validate --config <path-to-toml>
Run chaos with a config
cargo build
cargo run -- chaos --config chaosfilter.toml

Run cargo run -- init (or chaosfilter init after install) to write a starter config to the current directory.

Example TOML config

init writes a commented template; this is the same structure in shortened form. 

# ChaosFilter Example Configuration
#
# Usage:
#   chaosfilter chaos --config cf-config.toml
#
# This file defines:
#   - Targets (what to affect)
#   - Schedule (how long to apply chaos)
#   - Injectors (what kind of chaos to apply)

# --------------------------------------------------
# Plan Metadata
# --------------------------------------------------

name = "example-plan"

# --------------------------------------------------
# Schedule
# --------------------------------------------------

[schedule]
# Duration to keep chaos active (seconds)
duration_s = 10

# ==================================================
# Injectors
# ==================================================

# -----------------------------
# Network (tc netem)
# -----------------------------
[injectors.network_config]
enabled = false

# Network interface to target (for example: eth0, enp5s0, vethA)
# Use "default" to resolve the system default interface at load time.
target_iface = "default"

# Network delay in milliseconds
# delay_ms = 100

# Packet loss percentage (0.0 - 100.0)
# loss_percent = 10.0

# Cgroup attach points for network classifier
# Example: [117, 419, 666]
# network_ebpf_cgroup = [24059]

# -----------------------------
# CPU + Memory (cgroup v2)
# -----------------------------
[injectors.memory_config]
enabled = false

# PID to constrain
# target_pid = 12345

# Move PID into target cgroup before applying limits
# move_pid = true

# Controllers to enable in cgroup.subtree_control
# enable = ["cpu", "memory"]

# CPU quota/period
# Example: "20000 100000" = 20% of one CPU
# cpu_max = "20000 100000"

# CPU weight (1 - 10000)
# cpu_weight = 200

# Hard memory limit
# mem_max = "1G"

# Soft memory pressure threshold
# mem_high = "800M"

# Swap limit ("0" disables swap, "max" allows unlimited)
# swap_max = "0"

# -----------------------------
# Block I/O (cgroup v2 io)
# -----------------------------

# Block I/O Injector
[injectors.block_config]
enabled = false

# The target device that the I/O constraints will be applied to.
# device = "/dev/sda"

# Read bandwidth limit (bytes per second).
# rbps = 10485760

# Write bandwidth limit (bytes per second).
# wbpd = 10485760

# -----------------------------
# File Descriptor Exhaustion
# -----------------------------
[injectors.filesystem_config]
enabled = false

# PID whose process context will be targeted
# target_pid = 12345

# New soft RLIMIT_NOFILE value
# soft_limit = 64

# New hard RLIMIT_NOFILE value
# hard_limit = 128
